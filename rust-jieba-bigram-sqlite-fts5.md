# Rust + jieba-rs + CJK Bigram + SQLite FTS5 Contentless Search

## 1. Purpose

This document describes how to implement Traditional Chinese-friendly full-text search in a Rust application using:

- SQLite
- SQLite FTS5
- `jieba-rs`
- a custom CJK bigram tokenizer implemented in Rust
- FTS5 contentless-delete tables

The main goals are:

1. Good Traditional Chinese search recall.
2. Better semantic relevance than bigram-only search.
3. No dependency on an external search server such as Elasticsearch/OpenSearch.
4. Avoid storing a second full copy of every message inside the FTS table.
5. Keep the original message table as the source of truth.
6. Allow the entire search index to be deleted and rebuilt safely.
7. Support message insert, edit, and delete.
8. Keep the design compatible with future hybrid search such as BM25 + vector search + RRF.

The intended use case is a Rust Telegram message archival/search project, but the design is generic.

---

# 2. Core Idea

For each message, keep the original text only once in the normal SQLite table:

```text
messages.content
```

For example:

```text
今天下午在台北喝咖啡
```

Before inserting into the FTS index, Rust generates two derived token streams.

## Word-level tokens

Generated by `jieba-rs`:

```text
今天 下午 在 台北 喝 咖啡
```

## CJK bigram tokens

Generated deterministically by our own Rust code:

```text
今天 天下 下午 午在 在台 台北 北喝 喝咖 咖啡
```

Then insert both token streams into a contentless FTS5 table.

Conceptually:

```text
                         original message
                    今天下午在台北喝咖啡
                              │
              ┌───────────────┴────────────────┐
              │                                │
              ▼                                ▼
         jieba-rs                       CJK bigram
              │                                │
              ▼                                ▼
   今天 下午 在 台北 喝 咖啡      今天 天下 下午 ... 喝咖 咖啡
              │                                │
              └───────────────┬────────────────┘
                              ▼
                         SQLite FTS5
                          contentless
                              │
                              ▼
                       inverted index
                              │
                              ▼
                          message_id
                              │
                              ▼
                         messages table
                              │
                              ▼
                     complete original message
```

The FTS table is only an index.

The `messages` table remains the authoritative data source.

# 3. Why Use Both jieba-rs and Bigram?

`jieba-rs` provides word-level segmentation.

This is useful for semantic relevance.

For example:

```text
台北車站附近有咖啡店
```

A useful word segmentation might contain:

```text
台北車站
附近
咖啡店
```

These tokens are meaningful and therefore useful for BM25 ranking.

However, word segmentation is imperfect, especially for:

- Traditional Chinese
- Taiwanese vocabulary
- names
- technical terms
- uncommon product names
- abbreviations
- Telegram conversational text

If a tokenizer incorrectly segments a word, an exact lexical search may fail.

The bigram index acts as a robust fallback.

For example:

```text
台北車站
```

becomes:

```text
台北
北車
車站
```

Even if Jieba does not produce the exact word expected by the user, the overlapping bigrams provide a high-recall search path.

Therefore:

```text
jieba word index
    = better semantic precision

CJK bigram index
    = better recall / segmentation-independent matching
```

The hybrid approach uses both.

# 4. Why Not Use SQLite's Built-in Trigram Tokenizer?

SQLite FTS5 has a built-in `trigram` tokenizer.

However, it generates 3-character tokens.

Chinese queries are very often only two characters long:

```text
台北
咖啡
股票
硬碟
訊息
服務
```

A trigram tokenizer cannot generate a trigram for a two-character query.

For this project, a custom CJK **bigram** stream is more practical.

We generate bigrams in Rust and then feed them to the ordinary SQLite `unicode61` tokenizer.

Example:

```text
台北咖啡
```

Rust generates:

```text
台北 北咖 咖啡
```

SQLite only needs to understand that spaces separate tokens.

# 5. Why Contentless FTS5?

A normal FTS5 table stores:

1. the text inserted into the virtual table
2. the full-text index generated from the text

If we inserted both the Jieba token stream and bigram token stream into a normal FTS table, the database would effectively contain:

```text
original message
+
word-tokenized message
+
bigram-tokenized message
+
FTS indexes
```

That wastes storage because the tokenized forms are derived data.

They can always be regenerated from:

```text
messages.content
```

So use a contentless FTS5 table.

Recommended schema for SQLite 3.43 or newer:

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
    words,
    bigrams,
    content='',
    contentless_delete=1,
    tokenize='unicode61'
);
```

`content=''` tells SQLite not to keep a private copy of the indexed text.

`contentless_delete=1` provides easier `DELETE`, `UPDATE`, and `INSERT OR REPLACE` behavior than the older contentless mode.

This design still stores the actual FTS inverted index, because that is what makes searching fast.

It simply avoids storing another full copy of the derived text.

---

# 6. SQLite Version Requirement

`contentless_delete=1` requires SQLite 3.43.0 or newer.

At startup, verify the SQLite version:

```sql
SELECT sqlite_version();
```

If supporting SQLite older than 3.43 is required, either:

1. use traditional `content=''` mode and implement FTS5 delete commands correctly, or
2. require SQLite >= 3.43.

For a new Rust project, prefer requiring SQLite >= 3.43.

If using a bundled SQLite build through the Rust SQLite crate, verify that the bundled version satisfies this requirement.

# 7. Main Database Schema

The real message data should remain in an ordinary table.

Example:

```sql
CREATE TABLE messages (
    id                  INTEGER PRIMARY KEY,
    chat_id             INTEGER NOT NULL,
    telegram_message_id INTEGER NOT NULL,
    sender_id           INTEGER,
    content             TEXT NOT NULL,
    sent_at             INTEGER NOT NULL,

    UNIQUE(chat_id, telegram_message_id)
);
```

The FTS table:

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
    words,
    bigrams,
    content='',
    contentless_delete=1,
    tokenize='unicode61'
);
```

The fundamental relationship is:

```text
messages.id == messages_fts.rowid
```

Example:

```text
messages
-------------------------------------------------
id       content
123      今天下午在台北喝咖啡


messages_fts
-------------------------------------------------
rowid    words                 bigrams
123      [not stored]          [not stored]
```

Because the FTS table is contentless, querying its user columns will not return the inserted text.

The full-text index still contains the token/index information required to answer MATCH queries.

# 8. Important Storage Model

Do not think of `messages_fts` as a second message table.

Think of it as:

```text
token -> message IDs
```

Conceptually the underlying index resembles:

```text
word index:

台北
 ├─ 123
 ├─ 891
 └─ 912

咖啡
 ├─ 123
 └─ 456


bigram index:

台北
 ├─ 123
 ├─ 891
 └─ 912

北喝
 └─ 123

喝咖
 └─ 123

咖啡
 ├─ 123
 └─ 456
```

A search first finds matching `rowid` values.

The application then joins those IDs back to `messages`.

```rust
pub trait SearchTokenizer: Send + Sync {
    fn tokenize_words(&self, text: &str) -> Vec<String>;
    fn tokenize_bigrams(&self, text: &str) -> Vec<String>;

```

Implementation:

```rust
pub struct HybridChineseTokenizer {
    jieba: jieba_rs::Jieba,

```

The repository should receive this component by dependency injection.

Example:

```rust
let tokenizer = Arc::new(HybridChineseTokenizer::new());

let repository =
    SqliteMessageRepository::new(database, tokenizer);
```

Do not create a new Jieba instance for every message.

# 11. Text Normalization

Index-time and query-time normalization MUST be identical.

Recommended initial normalization:

```text
input
 ↓
Unicode NFKC normalization
 ↓
lowercase
 ↓
tokenization
```

Rust:

```rust
use unicode_normalization::UnicodeNormalization;

pub fn normalize_text(input: &str) -> String {
    input
        .nfkc()
        .collect::<String>()
        .to_lowercase()
}
```

This helps normalize cases such as:

```text
ＳＱＬｉｔｅ
```

into:

```text
sqlite
```

Do not perform Traditional-to-Simplified conversion in the first implementation.

That can be added later using OpenCC-style normalization if cross-script search is required.

# 12. jieba-rs Word Tokenization

Use search-oriented Jieba segmentation.

Conceptually:

```rust
let tokens = jieba.cut_for_search(&normalized, true);
```

Recommended implementation:

```rust
use jieba_rs::Jieba;

pub struct HybridChineseTokenizer {
    jieba: Jieba,
}

impl HybridChineseTokenizer {
    pub fn new() -> Self {
        Self {
            jieba: Jieba::new(),
        }
    }

    pub fn tokenize_words(&self, text: &str) -> Vec<String> {
        let normalized = normalize_text(text);

        self.jieba
            .cut_for_search(&normalized, true)
            .into_iter()
            .map(str::trim)
            .filter(|token| !token.is_empty())
            .filter(|token| !token.chars().all(char::is_control))
            .map(ToOwned::to_owned)
            .collect()
    }
}
```

The exact `jieba-rs` API should be checked against the selected crate version when implemented.

# 14. CJK Bigram Generation

The bigram tokenizer should primarily generate overlapping pairs for contiguous CJK text.

Example:

```text
台北咖啡很好喝
```

becomes:

```text
台北
北咖
咖啡
啡很
很好
好喝
```

Do not blindly bigram the entire Unicode string across whitespace and punctuation.

For example:

```text
台北 GitLab Runner 咖啡
```

should not generate nonsense cross-boundary pairs such as:

```text
北g
```

The bigram implementation should recognize CJK sequences and generate bigrams inside each contiguous sequence.

---

# 15. Detecting CJK Characters

A practical implementation can initially recognize common Han ranges.

For example:

```rust
fn is_cjk(c: char) -> bool {
    matches!(
        c as u32,
        0x3400..=0x4DBF     // CJK Extension A
        | 0x4E00..=0x9FFF   // CJK Unified Ideographs
        | 0xF900..=0xFAFF   // CJK Compatibility Ideographs
        | 0x20000..=0x2A6DF // Extension B
        | 0x2A700..=0x2B73F
        | 0x2B740..=0x2B81F
        | 0x2B820..=0x2CEAF
        | 0x2CEB0..=0x2EBEF
        | 0x30000..=0x3134F
    )
}
```

This can be refined later.

Avoid hardcoding assumptions that one Rust byte equals one Chinese character.

Always operate on Rust `char` values, not UTF-8 byte offsets.

# 16. Bigram Algorithm

Recommended behavior:

```text
input:
今天去台北喝咖啡

CJK sequences:
今天去台北喝咖啡

bigrams:
今天
天去
去台
台北
北喝
喝咖
咖啡
```

For a single CJK character, keep the unigram as a fallback.

Example:

```text
我
```

becomes:

```text
我
```

**Correction:** this only finds messages where the character appears as an isolated CJK run. A single-character query must not rely on this (see §65 for the project decision: single-character queries use a `LIKE` scan).

Example implementation:

```rust
pub fn cjk_bigrams(text: &str) -> Vec<String> {
    let normalized = normalize_text(text);

    let mut result = Vec::new();
    let mut current = Vec::<char>::new();

    fn flush(sequence: &mut Vec<char>, output: &mut Vec<String>) {
        match sequence.len() {
            0 => {}
            1 => {
                output.push(sequence[0].to_string());
            }
            _ => {
                for pair in sequence.windows(2) {
                    output.push(pair.iter().collect());
                }
            }
        }

        sequence.clear();
    }

    for ch in normalized.chars() {
        if is_cjk(ch) {
            current.push(ch);
        } else {
            flush(&mut current, &mut result);
        }
    }

    flush(&mut current, &mut result);

    result
}
```

# 17. English and Technical Text

The bigram column should mainly exist for CJK characters.

Do not generate character bigrams such as:

```text
gitlab

gi
it
tl
la
ab
```

unless there is a demonstrated need.

English and technical terms are already handled better by the word-index path and SQLite's normal tokenization.

The Jieba word stream should preserve useful ASCII terms such as:

```text
gitlab
runner
chromium
sqlite
fts5
192.168.1.10
```

If real-world testing shows poor tokenization of technical terms, add a lightweight ASCII token extractor and merge those tokens into the `words` stream.

Do this only after measuring actual behavior.

# 18. Deduplication

Search-mode Jieba may emit overlapping terms.

The bigram generator may also produce repeated tokens.

It is reasonable to preserve repeated words if term frequency is desired for BM25.

Do not automatically deduplicate every token unless testing shows it improves relevance.

For example:

```text
咖啡 咖啡 咖啡
```

should normally retain term frequency information.

However, avoid accidentally inserting duplicated derived tokens caused by combining multiple tokenization pipelines incorrectly.

# 19. Generate Index Payload

Create a type:

```rust
pub struct SearchDocument {
    pub words: String,
    pub bigrams: String,
}
```

Build it as:

```rust
impl HybridChineseTokenizer {
    pub fn build_document(&self, text: &str) -> SearchDocument {
        let words = self.tokenize_words(text).join(" ");
        let bigrams = self.tokenize_bigrams(text).join(" ");

        SearchDocument {
            words,
            bigrams,
        }
    }
}
```

Example:

```text
input:
今天下午在台北喝咖啡

words:
今天 下午 在 台北 喝 咖啡

bigrams:
今天 天下 下午 午在 在台 台北 北喝 喝咖 咖啡
```

# 20. Insert Flow

When a Telegram message arrives:

```text
message received
      │
      ▼
normalize/tokenize
      │
      ▼
BEGIN TRANSACTION
      │
      ├── INSERT messages
      │
      └── INSERT messages_fts
      │
      ▼
COMMIT
```

Example SQL:

```sql
INSERT INTO messages (
    chat_id,
    telegram_message_id,
    sender_id,
    content,
    sent_at
)
VALUES (?, ?, ?, ?, ?);
```

Get the new message ID.

Then:

```sql
INSERT INTO messages_fts(
    rowid,
    words,
    bigrams
)
VALUES (?, ?, ?);
```

Rust-like example:

```rust
let search_doc = tokenizer.build_document(&message.content);

let tx = conn.transaction()?;

tx.execute(
    r#"
    INSERT INTO messages (
        chat_id,
        telegram_message_id,
        sender_id,
        content,
        sent_at
    )
    VALUES (?, ?, ?, ?, ?)
    "#,
    params![
        message.chat_id,
        message.telegram_message_id,
        message.sender_id,
        message.content,
        message.sent_at,
    ],
)?;

let id = tx.last_insert_rowid();

tx.execute(
    r#"
    INSERT INTO messages_fts(rowid, words, bigrams)
    VALUES (?, ?, ?)
    "#,
    params![
        id,
        search_doc.words,
        search_doc.bigrams,
    ],
)?;

tx.commit()?;
```

The FTS row and source message must be updated atomically.

# 21. What Is Actually Stored?

Although the application executes:

```sql
INSERT INTO messages_fts(rowid, words, bigrams)
VALUES (
    123,
    '今天 下午 台北 咖啡',
    '今天 天下 下午 ... 台北 ... 咖啡'
);
```

because the table is contentless, FTS5 does not keep those two complete strings as ordinary stored document columns.

It extracts tokens and stores the full-text index.

The authoritative text remains:

```text
messages.content
```

This reduces duplication significantly compared with a normal FTS table.

However, the index itself still consumes disk space.

Using both `words` and `bigrams` means the search index will be larger than using a single lexical index.

That is intentional.

The design trades index space for search quality while avoiding a complete duplicate copy of each derived tokenized document.

# 22. Query Processing

A user query must be processed using the same normalization/tokenization rules.

Example query:

```text
台北咖啡
```

Generate:

```text
word query:
台北 咖啡

bigram query:
台北 北咖 咖啡
```

Then query both FTS columns.

There are several possible strategies.

The initial implementation should prefer a simple, predictable weighted query.

---

# 23. Recommended Search Strategy

Use word matching as the primary path and bigram matching as recall support.

Conceptually:

```text
word matches      high importance
bigram matches    lower importance
```

FTS5 allows column-specific queries.

Example:

```sql
SELECT
    m.*,
    bm25(messages_fts, 5.0, 1.0) AS rank
FROM messages_fts
JOIN messages AS m
    ON m.id = messages_fts.rowid
WHERE messages_fts MATCH ?
ORDER BY rank ASC
LIMIT ? OFFSET ?;
```

The first BM25 weight corresponds to `words`.

The second corresponds to `bigrams`.

Example weights:

```text
words:   5.0
bigrams: 1.0
```

These are tuning parameters, not universal constants.

Benchmark them against real data.

---

# 24. Building Safe FTS5 Queries

Do not put raw user input directly into `MATCH`.

FTS5 has its own query grammar.

Characters or tokens such as:

```text
"
*
-
AND
OR
NOT
NEAR
```

may change query meaning.

Use bound SQL parameters **and** construct a safe FTS expression.

A useful helper:

```rust
fn quote_fts_term(term: &str) -> String {
    format!("\"{}\"", term.replace('"', "\"\""))
}
```

For tokens:

```text
台北
咖啡
```

build:

```text
"台北" AND "咖啡"
```

---

# 25. Column-Specific Query

Given:

```rust
word_tokens = ["台北", "咖啡"]
bigram_tokens = ["台北", "北咖", "咖啡"]
```

A possible FTS expression is:

```text
words:("台北" AND "咖啡")
OR
bigrams:("台北" AND "北咖" AND "咖啡")
```

The exact query grammar should be verified with FTS5 tests.

Another robust implementation is to perform separate word and bigram searches and merge the results in Rust.

That makes behavior easier to understand and tune.

# 26. Recommended Initial Retrieval Design

For the first version, use **two independent FTS queries**.

## Word query

```sql
SELECT
    rowid,
    bm25(messages_fts, 5.0, 0.0) AS rank
FROM messages_fts
WHERE words MATCH ?
ORDER BY rank
LIMIT ?;
```

## Bigram query

```sql
SELECT
    rowid,
    bm25(messages_fts, 0.0, 1.0) AS rank
FROM messages_fts
WHERE bigrams MATCH ?
ORDER BY rank
LIMIT ?;
```

Then combine the IDs in Rust.

This is easier to debug than one complicated FTS expression.

Later, replace it with one query if benchmark results justify doing so.

# 27. Result Fusion

A simple first implementation can rank:

```text
word match first
bigram-only match second
```

A more general approach is Reciprocal Rank Fusion.

For example:

```text
word search top 100
+
bigram search top 100
        │
        ▼
       RRF
        │
        ▼
   merged top 100
```

Formula:

```text
RRF score = Σ 1 / (k + rank)
```

Common `k` values such as `60` can be used as a starting point.

This is especially attractive because the project may later add:

```text
Qdrant vector search
```

Then the exact same fusion layer can combine:

```text
word BM25
+
bigram BM25
+
vector similarity
```

---

# 28. Simpler Alternative

If RRF is unnecessary initially, use one combined FTS query and weighted BM25.

That implementation is smaller.

Recommended development sequence:

```text
Phase 1:
combined FTS + weighted BM25

Phase 2:
measure quality

Phase 3:
if needed, split into independent retrieval lists + RRF
```

Do not introduce complex ranking before measuring the simpler implementation.

# 29. Recover Complete Messages

The FTS result only needs to identify matching `rowid` values.

Fetch the real message by joining:

```sql
SELECT
    m.id,
    m.chat_id,
    m.telegram_message_id,
    m.sender_id,
    m.content,
    m.sent_at,
    bm25(messages_fts, 5.0, 1.0) AS rank
FROM messages_fts
JOIN messages AS m
    ON m.id = messages_fts.rowid
WHERE messages_fts MATCH ?
ORDER BY rank ASC
LIMIT ? OFFSET ?;
```

The application should never rely on `messages_fts.words` or `messages_fts.bigrams` to recover source text.

They are contentless.

# 30. Message Updates

Telegram messages can be edited.

With `contentless_delete=1`, update all FTS columns together.

Flow:

```text
new original text
      │
      ▼
regenerate words + bigrams
      │
      ▼
BEGIN
      │
      ├── UPDATE messages
      └── UPDATE messages_fts
      ▼
COMMIT
```

Example:

```sql
UPDATE messages_fts
SET
    words = ?,
    bigrams = ?
WHERE rowid = ?;
```

All user-defined FTS columns should be supplied when updating a contentless-delete table.

Example Rust:

```rust
let doc = tokenizer.build_document(&new_content);

let tx = conn.transaction()?;

tx.execute(
    "UPDATE messages SET content = ? WHERE id = ?",
    params![new_content, id],
)?;

tx.execute(
    r#"
    UPDATE messages_fts
    SET words = ?, bigrams = ?
    WHERE rowid = ?
    "#,
    params![doc.words, doc.bigrams, id],
)?;

tx.commit()?;
```

# 31. Message Deletes

With `contentless_delete=1`:

```sql
DELETE FROM messages_fts
WHERE rowid = ?;

DELETE FROM messages
WHERE id = ?;
```

Run both in the same transaction.

Example:

```rust
let tx = conn.transaction()?;

tx.execute(
    "DELETE FROM messages_fts WHERE rowid = ?",
    [id],
)?;

tx.execute(
    "DELETE FROM messages WHERE id = ?",
    [id],
)?;

tx.commit()?;
```

# 32. Why Prefer contentless-delete Over Old Contentless Mode?

The original contentless mode:

```sql
content=''
```

has restrictions around ordinary `DELETE` and `UPDATE`.

Historically, applications needed special FTS5 delete commands and had to provide the old indexed text to remove index entries correctly.

For this project, that is unnecessarily awkward.

Using:

```sql
content='',
contentless_delete=1
```

on SQLite >= 3.43 provides simpler CRUD behavior while retaining the storage advantage of a contentless index.

Therefore this project should prefer contentless-delete.

---

# 33. Do Not Set columnsize=0 Initially

FTS5 also allows:

```sql
columnsize=0
```

which can save some additional space.

Do not enable it initially.

BM25 ranking and token statistics are useful for this search design.

Optimize index size only after measuring real disk usage and ranking requirements.

Initial schema:

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
    words,
    bigrams,
    content='',
    contentless_delete=1,
    tokenize='unicode61'
);
```

Keep the default column-size metadata.

# 34. Rebuilding the Index

The search index must be considered disposable.

A rebuild is required when any of the following changes:

- Jieba version
- Jieba dictionary
- custom dictionary
- normalization rules
- bigram rules
- technical token extraction
- Traditional/Simplified normalization
- FTS schema
- ranking/index strategy

Provide an application operation such as:

```text
telegram-cli search rebuild-index
```

Algorithm:

```text
DELETE all FTS index entries

for every message:
    regenerate word tokens
    regenerate bigrams
    insert into messages_fts
```

For contentless FTS tables, use the appropriate FTS5 `delete-all` command when rebuilding if required by the chosen SQLite behavior.

A safe implementation may also:

1. drop the FTS table
2. recreate it
3. backfill all rows

Since the FTS table contains no authoritative data, dropping and rebuilding it is safe.

# 38. Bigram Query Semantics

Be careful when using `AND` with all generated bigrams.

For a query:

```text
台北咖啡
```

bigrams are:

```text
台北
北咖
咖啡
```

**Correction:** requiring all three with `AND` does NOT guarantee a contiguous sequence; the bigrams may occur at unrelated positions. Use an FTS5 **phrase query** on the bigram column instead:

```text
bigrams:"台北 北咖 咖啡"
```

A phrase requires the tokens to be adjacent and in order, which is the intended substring-style fallback. (Known minor false positive: a phrase can span the boundary between two separate CJK runs that are adjacent in the token stream; acceptable.)

But the word query:

```text
台北 AND 咖啡
```

can match:

```text
台北有很多好喝的咖啡
```

Therefore the two indexes answer slightly different questions:

```text
word index:
contains the concepts/words

bigram index:
contains the character sequence or highly overlapping sequence
```

That difference is useful.

# 39. Very Short Queries

A custom bigram implementation should retain a single CJK character as a unigram.

For example:

```text
台
```

indexes/searches as:

```text
台
```

For two characters:

```text
台北
```

indexes/searches as:

```text
台北
```

This avoids the short-query limitation of SQLite's trigram tokenizer for queries of two or more characters. Single-character queries are handled separately (§65).

# 52. Performance

Tokenization occurs once when:

- inserting
- editing
- rebuilding the index

Search performs:

- query normalization
- Jieba query tokenization
- bigram query generation
- FTS lookup

This is usually much cheaper than scanning message text with:

```sql
LIKE '%...%'
```

for large collections.

The index uses additional disk space, but avoids storing duplicate full tokenized documents due to the contentless configuration.

---

# 53. Storage Expectations

Do not expect contentless FTS to make the index free.

The database still contains:

```text
original message data
+
word inverted index
+
bigram inverted index
+
FTS metadata
```

The bigram index may contain significantly more terms than the Jieba word index.

However, it does **not** contain:

```text
another ordinary stored copy of every word-tokenized message
+
another ordinary stored copy of every bigram-tokenized message
```

That is the main storage benefit of contentless FTS5.

Measure real database size after indexing representative data.

Do not estimate storage exclusively from raw text size.

# 54. FTS Maintenance

FTS5 uses internal B-tree segments.

Large numbers of writes may create multiple segments that are merged over time.

Do not manually optimize this until real performance measurements show a need.

Possible future operational commands may include FTS5 optimize/merge maintenance.

Treat this as an optimization phase rather than part of initial correctness.

# 63. Final Design Summary

The design deliberately separates three responsibilities:

```text
jieba-rs
    │
    └── understands likely Chinese word boundaries

custom CJK bigram generator
    │
    └── provides segmentation-independent recall

SQLite FTS5
    │
    └── builds/searches the inverted index and provides BM25
```

Data ownership remains:

```text
messages
    = source of truth

messages_fts
    = disposable derived search index
```

The key storage optimization is:

```sql
content=''
```

which prevents FTS5 from keeping another ordinary copy of the tokenized document text.

For SQLite 3.43+, add:

```sql
contentless_delete=1
```

so message edits and deletes remain straightforward.

The resulting architecture gives the Rust application:

- word-level Chinese relevance from Jieba
- robust Traditional Chinese fallback from bigrams
- SQLite-native indexed search
- BM25 ranking
- low operational complexity
- no external search server
- no duplicate full tokenized document storage
- an easy path toward future vector + RRF hybrid retrieval

# 65. Project Adjustments for tgarchive (authoritative; overrides earlier sections where they conflict)

Reviewed against the actual tgarchive codebase (SQLx, bundled SQLite 3.46.0, `messages.row_id` as rowid, soft deletes, cursor pagination, web UI).

## 65.1 Schema and migration
- Replace the current external-content FTS (`content='messages'`, `tokenize='unicode61'`) and its three triggers (`messages_fts_insert/delete/update`) with:
  ```sql
  CREATE VIRTUAL TABLE messages_fts USING fts5(
      words, bigrams,
      content='', contentless_delete=1,
      tokenize='unicode61'
  );
  ```
  `rowid == messages.row_id`. Drop the triggers: SQL triggers cannot call jieba.
- Add `app_metadata(key TEXT PRIMARY KEY, value TEXT NOT NULL)` with `search_index_version` and a `search_index_state` (`ready` | `rebuilding` | `stale`).
- The SQL migration only creates/drops structures. Backfill needs Rust tokenization, so it happens in `db init` (automatically when the version is missing/stale) and via `tgarchive search rebuild-index`. Rebuild runs in batched transactions and reports progress.
- Until the index is `ready`, text search falls back to a `LIKE` scan and the API/UI reports that the index is rebuilding.

## 65.2 Write path
- Index maintenance moves into the Rust write path, in the same transaction as the message write (the ingest writer batch).
- Only (re)index when new text was actually written: the upsert has version/priority guards (history must not overwrite newer realtime edits). Use `RETURNING` (or an equivalent check) to know whether the row changed.
- Messages with NULL/empty text are not indexed (delete any existing FTS row for them).
- **Soft delete keeps the index entry.** tgarchive marks `is_deleted=1` and keeps the text; search filters with `m.is_deleted` and supports `include_deleted`. Only a physical row delete removes the FTS row.

## 65.3 Query semantics
- Normalization identical at index and query time: NFKC + lowercase.
- Query = `words:(w1 AND w2 ...) OR bigrams:"b1 b2 ..."` (bigram path as a **phrase** per contiguous CJK run; multiple runs/ASCII terms combined with AND). All terms quoted; user text never reaches MATCH unescaped.
- Drop single-character CJK function words (e.g. 的 了 在 是 和 與 及 也 就 都 而 及 或) from the **word** query only; the bigram path keeps everything.
- **Single-character query** (one CJK char, no other terms): use a `LIKE '%字%'` scan on `messages.text` with the same filters (documented as slower). Index does not store unigrams.
- Ranking: `bm25(messages_fts, 5.0, 1.0)` (words, bigrams); weights are tuning parameters.

## 65.4 API
- `GET /api/v1/messages/search` keeps plain-text `q` (no FTS grammar exposed) and gains `sort=relevance|time`; **default `relevance` when `q` is present**.
  - `time`: existing keyset cursor pagination, unchanged.
  - `relevance`: opaque cursor encoding (rank, row_id) or an offset-based cursor; cursor format is versioned/opaque to clients.
- Contentless tables cannot use FTS5 `snippet()`/`highlight()`. Produce a short snippet in Rust around the first match (by char offsets on the original text) and return it as `snippet`; keep client-side highlighting in the UI.
- Expose index status in `/api/v1/status` (`search_index: { version, state, indexed, total }`).

## 65.5 UI
- Search page: sort toggle (相關性 / 時間, default 相關性), show snippet, show a banner when the index is rebuilding / single-character LIKE mode, update the FTS limitation note (Chinese substrings now supported via bigrams).

## 65.6 Tests (in addition to §43–§50)
- Contiguity: `台北咖啡` must not match `台北…北咖…咖啡` scattered text.
- Single-character query finds the char at word end (`北` in `台北`).
- Soft-deleted message: hidden by default, found with `include_deleted=true`.
- Stale history upsert does not change the index; a newer realtime edit re-indexes.
- Migration from the 0005 schema: old FTS/triggers removed, rebuild fills the index, search works; LIKE fallback while not ready.
- Relevance pagination is stable (no duplicates/gaps across pages).
- E2E (Playwright fixture): Chinese substring search, sort toggle, snippet.
- A small evaluation script/test over the fixture with expected hits for representative queries (台北, 台北咖啡, 伺服器, GitLab Runner, chromium, 硬碟).

# Implementation notes (tgarchive)

All §65 items are implemented. Code map: `migrations/0006_search_index.sql`, `src/infrastructure/search/{normalize,bigram,tokenizer,query,snippet}.rs`, `src/infrastructure/persistence/sqlite/{search,store}.rs`, `src/interface/{cursor,cli}.rs`, `src/interface/rest/{routes,dto}.rs`, `web/src/pages/SearchPage.tsx`.

- **65.1 Schema/migration** — done. Metadata keys `search_index_version`, `search_index_state` (`ready`/`rebuilding`/`stale`). A database with no indexable text is marked `ready` by the migration itself (so fresh databases and tests need no rebuild); otherwise `stale`. `DELETE FROM messages_fts` is used instead of the FTS5 `delete-all` command (not available for contentless-delete tables). `db init` rebuilds automatically; `tgarchive search rebuild-index` / `search status`; `serve` never blocks on a rebuild (warns, reports state, LIKE fallback). Not implemented: rebuilding inside `serve`.
- **65.2 Write path** — done in `write_batch` (same transaction). Instead of `RETURNING`, the previous text is read before the guarded upsert and compared after `rows_affected() > 0`; `INSERT OR REPLACE` into the FTS table. NULL/empty text is deleted from the index. Soft deletes keep entries.
- **65.3 Query semantics** — done. Bigram path: one phrase per CJK run of >= 2 chars; ASCII terms of a mixed query are required in the `words` column on that path. Single-character CJK runs become extra `LIKE` terms (ANDed), a pure single-character query is a LIKE scan. Function-word list: 的 了 在 是 和 與 与 及 也 就 都 而 或 跟. Also: tokens without any alphanumeric char are dropped (they would become empty FTS phrases). Consequence worth knowing: the *word* path requires all words but not adjacency, so `台北咖啡` also matches `台北車站附近的咖啡`; the §65.6 "contiguity" test therefore asserts the bigram phrase on the index directly (and `北咖啡` end-to-end).
- **65.4 API** — done: `sort`, `snippet`, `search_index` in `/status`. Relevance cursor is an offset (`{"version":1,"kind":"relevance","offset":N}`, base64url, max offset 100000), passed back as `before`; keyset cursors and offset cursors are rejected for the wrong sort. When the index is unusable or the query is LIKE-only, relevance sort orders by time (still offset-paged). Snippet is computed by char-wise NFKC mapping (`snippet.rs`).
- **65.5 UI** — done (sort toggle, snippet, banners for stale/rebuilding index and single-character mode, updated note, status page row, Intl.Segmenter highlighting).
- **65.6 Tests** — done (see IMPLEMENTATION_STATUS.md). Evaluation set: 台北, 台北咖啡, 伺服器, GitLab Runner, chromium, 硬碟, ＳＱＬｉｔｅ in `tests/search.rs::evaluation_set_finds_expected_messages` and the E2E fixture.
- **Deviations / not done**: no custom jieba user dictionary (§13), no `search verify-index` (§51; `search status` compares indexed vs total), no OpenCC (§40), bigrams for Han only (§15 list), search max length stays 4096 bytes.
- **English prefix matching** — ASCII alphanumeric query terms of length >= 3 become FTS5 prefix queries (`"term"*`, still quoted so injection-safe; `query.rs::quote_term`) on both the words path and the ASCII terms of the mixed bigram path; shorter terms and CJK bigram phrases stay exact. No `prefix=` index added (would require a table rebuild and `search_index_version` bump); the prefix scan on the unicode61 term list was not found necessary at this scale. Snippets/highlights already match by substring, so the matched word prefix is located and marked.
- **Search URL state** — `/search?q=&chat=&from=&to=&include_deleted=1&sort=time` is the single source of truth; keystrokes update `q` after the debounce with `replace`, filter changes push history entries, so back from a result's chat context restores the same results.
- **Quality evaluation and benchmark** — `tests/search_quality.rs` (ground truth independent of the index; definitions in its header: CJK runs >= 2 chars contiguous, single chars raw-text substring, ASCII terms exact (<3) / prefix (>=3); words-path extras must be "explained"; ranking sanity: top-1 exact, >= 0.8 exact in top-10) and `examples/search_bench.rs` (shared generator in `tests/support/`; `--db` runs on a temp copy). Reference numbers: 100k all budgets PASS (typical p95 < 30 ms); 1M p95 246 ms for the most common word, 1.3-1.9 s for full single-char LIKE scans, ~1.1 s for relevance offset 90000. Finding fixed: with chat/sender filters the planner drove the query from the chat/sender index and probed FTS per row (146-400 ms at 100k); `+m.chat_id`/`+m.sender_id` in `list_messages` when a MATCH is present makes FTS hits drive it (identical results).
